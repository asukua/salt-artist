## 0.3.4 歌曲入口、动画与原生歌曲交互

主页歌曲区标题改为「全部歌曲」，标题仍打开独立歌曲页；右侧原「显示全部」位置改为对艺人完整歌曲队列随机播放。保留 0.3.3 的三行、多列、列优先顺序、搜索和返回位置；下文 0.3.3 的单列独立页及旧入口描述保留为历史记录，本节替代其当前实现。

翻页期间同时保留离场页与入场页，在相同裁剪区域内按方向横向移动，结束后释放离场页；避免先替换内容再播放入场动画造成闪现。动画使用 Compose `Animatable` 与 `spring(stiffness = 500f)`，跟随帧时钟及 `MotionDurationScale`，不使用固定次数的延时循环。页码、方向及切换状态在组合阶段捕获，绘制阶段只读取进度；否则 LaunchedEffect 可能在新页建立之前移动旧层，实际逐帧测试曾捕获第一帧闪空。独立歌曲页继续由艺人页内部状态切换，不新增宿主路由；其进入和返回参照已核实的椒盐桌面导航：进入时新页从 `(0, 150px)` 滑入、旧页淡出，返回时主页淡入、歌曲页向下滑出并淡出，阻尼比为 1、弹簧刚度为 500。这里的 500 是刚度，不是时长；宿主 iOS 分支的 500ms 与贝塞尔参数不用于桌面页面。

全部歌曲页优先复用宿主 `TrackLazyColumn`，沿用椒盐的歌曲表格／列表外观、选择、播放和右键能力；主页预览及插件降级行复用 `TrackContextMenu`。原始宿主 `Track` 从原有添加时间所用的同一次 raw query 保存为 ID 映射，避免右键时再次查询，也不从 Workshop `MediaItem` 拼造缺失字段。仅已核实的 1.19.3 profile 启用这些桥接；自定义歌曲字段与原始值不一致、旧宿主、反射契约或当前 CompositionLocal 不满足时，保留可用的插件表格与基础右键。原生歌曲页的文字和背景统一跟随宿主主题，避免黑字叠在头图深色背景上。具体入口与守卫见[宿主兼容说明](host-compatibility.md#034-歌曲界面兼容)。

搜索时继续使用插件表格，将原始曲目交回完整艺人队列播放。宿主 `TrackLazyColumn` 会把输入的分组作为播放队列，唯一的 `Function2` 参数实际是空态 composable，不能覆盖行播放；因此不向原生列表传入搜索子集，以保留既有搜索播放行为。进入时原始 Track 尚未就绪则本次保留插件表格，避免后台查询完成后替换已滚动的列表；下次进入可启用已经就绪的原生列表。

原生桌面菜单调用链尚未发现明确的动画参数，不能把页面导航的弹簧参数推定为菜单时长。原生菜单不再叠加插件动画，以免重复变换、影响鼠标定位或子菜单。插件自己的信息、编辑和目录弹窗统一使用弹簧淡入淡出；弹出菜单仍沿用原实现。

本轮 `test testHostRuntime plugin` 通过：完整 JDK 与宿主模块范围各 283 项测试，另有 9 项真实 Compose／Skia 离屏测试通过。前后翻页各记录 27 帧，所有帧保持可见封面；中间位移、旧页语义隐藏、动画期禁用点击、搜索／数据／列数变更重置、结束归位和返回原页位置均通过。另验证页面 push/pop、弹窗真实像素淡入淡出、基础右键及原始曲目回调、5,000 首惰性列表和 1,500 张缩略图离线恢复。报告与安装包 SHA-256 位于 `build/reports/artwork-034/verification.json`，翻页 GIF 位于 `build/reports/song-context-034/song-paging-0.3.4.gif`。

维护脚本 `scripts/verify-host.py` 在本机 1.19.3 通过 135 项 class／ABI 检查，包含本轮歌曲与动画入口；证据位于 `build/reports/song-context-034/maintained-check/`。安装包保留已发布 0.3.2 的 14 个设置、2 个字体和 123 个顶级类，双 Manifest 版本均为 0.3.4，权限一致，无宿主运行时或测试类混入。离屏测试验证插件组合及降级路径，签名复核验证接入契约，两者均不能替代实际宿主中的右键动作、子菜单、主题切换和播放验收；本轮未进行宿主窗口交互验收。

## 0.3.2 大曲库与静态封面

[#1](https://github.com/asukua/salt-artist/issues/1) 的封面丢失与 [#2](https://github.com/asukua/salt-artist/issues/2) 的大量歌曲闪退反馈触发本轮修复。源码确认：详情把完整曲库放进单个 LazyColumn item，再用普通 Column 创建所有歌曲与专辑；封面仅缓存 128 项，可见组件直接读取缓存；累计请求计数只增不减，约 513 次后拒绝所有新请求。0.3.1 取消的是动态视频磁盘淘汰，不能覆盖这些静态封面路径。未取得报告者的崩溃日志，不能据此把闪退根因认定为已证实的 OOM。

保持现有布局、列宽阈值、列优先歌曲顺序、最新添加位置和播放/导航回调。概览只组合前三行，剩余歌曲与专辑行接入同一个外层惰性列表；不增加内层独立滚动区。搜索也按需组合。`CatalogSongLayout` 集中计算分栏索引，避免惰性化后改变原有顺序或漏掉不足一列的歌曲。

按用户要求取消静态曲库封面的项数淘汰、累计请求次数与回退头图的 4 项限制，不引入新的保留数量或总容量上限。编码缩略图保存于插件目录 `library-covers/`，直到显式清除；解码图片由可见组件请求持有，离开组合后只留弱引用，允许 GC 回收，返回时从本地缩略图恢复。歌曲行使用最长边 96px、目录回退封面 320px、专辑及头图回退 640px，不放大原图；头图继续单独生成原有模糊档位。艺人资料、Apple Music 大图及头像沿用原有独立缓存策略。

只控制工作并发：两个 worker 在真正开始任务后才向宿主获取封面并解码，待处理条目不持有原始图片字节。相同 key 的可见组件共享任务，最后一个组件离开后移除待处理任务；已开始的任务完成时拒绝过期发布。请求对象同时处理组合销毁和放弃，避免惰性预组合留下无主请求。清除/停用推进代次，磁盘原子写入与结果发布受同一代次锁保护，防止迟到结果恢复已清内容。失败在重新获取该条目时可重试，不启动无限重组重试。

不采用无限强引用位图缓存：移除数量限制仍须避免浏览过的所有图片永久驻留解码内存。也不整体删掉图片尺寸和损坏输入校验；这些约束保护解码器，与用户要求取消的缓存保留配额分开。清除缓存同步包含新增曲库缩略图及计数。

验证入口：常规 `test testHostRuntime plugin`；Windows 的 `scripts/verify-artwork.init.gradle` 增加真实 Skia/Compose 离屏测试，不把 native 测试依赖打入插件。测试对照 Git 中的 0.3.1 原始目录布局，参考实现仅替换图片获取接口以适应新请求生命周期。

本轮 274 项单元测试在完整 JDK 与宿主模块范围下各通过一次，另有 3 项真实 Skia/Compose 测试通过。实际解码并保存 1,500 张缩略图，验证可见引用不丢失、重启后在禁用宿主取图入口时恢复边界封面、头图五档模糊，以及显式清除 1,501 个文件。5,000 首歌曲场景完成 600 行跳转、专辑区、返回、收起与搜索；完整场景向模拟宿主来源取图少于 250 次，未全量请求 5,000 张图片。500/1000/1400px 三档宽度各验证预览、展开、搜索，9 组截图与 0.3.1 参考布局像素差异均为 0。原包 14 个设置、2 个字体资源及 120 个顶级类的保留检查通过，包内双 Manifest 的 0.3.2 版本和权限一致，无测试或新增 native 依赖混入。证据位于 `build/reports/artwork-032/`；宿主窗口与报告者实际曲库不属于本次离屏验证，仍不能把这组结果当作原始闪退日志的根因证明。

## 0.3.1 动态头图首帧等待

用户明确反馈的是头图先静止片刻、其他操作正常。日志中已缓存的 4K 首帧约需 0.4～0.7 秒。分阶段测试发现每页新建 renderer 仅约 3～11ms，主要有一段固定约 200ms：SW 目标等 `dwidth/dheight` 通知后才渲染，而 libmpv 的首次 flip 又等待首帧被消费，直到超时才继续通知尺寸。与 [libmpv 的首次 flip 等待](https://github.com/mpv-player/mpv/blob/master/video/out/vo_libmpv.c) 一致，不能通过删除显示同步或降低清晰度掩盖。

仅在 CPU renderer 初始化时尝试 `video-latency-hacks=yes`，不整体套用低延迟 profile。该选项跳过首次/seek 的渲染等待，同时将持续播放 lookahead 减少到一帧；因此验证了后续帧率和内容变化，不能只看第一张图。选项不支持时忽略返回码，旧宿主继续使用原 CPU 后端。原分辨率选流、24/30 帧目标、解码线程数、静音、缓存和离页释放均保留，不跨页常驻播放器。官方选项说明见 [mpv manual](https://mpv.io/manual/stable/#options-video-latency-hacks)。

两段实际 3840×2160 缓存视频、每项三轮的同条件诊断中，首帧中位耗时分别从 402.8ms 降到 158.7ms、从 421.3ms 降到 171.3ms，持续约 25fps，与原方案一致；首帧非黑且采样内容一致。修改 lavf 探测参数没有稳定收益；单解码线程降低持续帧率，均未采用。已知真实尺寸后提前渲染也能去掉等待，但不能把所选分辨率猜作实际尺寸，故不引入该路径。

247 项测试在完整 JDK 和宿主模块范围下通过。另用宿主运行时、宿主 native 库和最终生产 `SoftwareVideoFrames` 复核首帧、真实尺寸、连续变化帧及资源释放；可复用入口为 `scripts/MotionStartupProbe.java`，证据在 `build/reports/motion-startup/`。这些耗时从 decoder 打开到 CPU raster 就绪，未包含资料/海报加载、界面首次绘制或网络首次取流，不能据此承诺页面零延迟。

## 0.3.1 预下载与总列表背景

问题与约束：第一次打开详情页需要等待身份、地区、资料和图片请求，已下载资料也不能等待联网完成才出现。艺术家总列表的背景提供跟随椒盐设置和自定义两项，同时保留宿主搜索、排序、收藏标记、分组、网格、导航与迷你播放器。设置只作用于总列表，详情页继续保持原先的沉浸式配色。

详情页分开进行本地缓存解码和远程检查；本地任务走图片 worker，即使串行网络 worker 正在等待也能先发布已有简介和图片。每次进入页面检查缓存时间，一天内复用，超过一天重新解析元数据；地址、裁剪或头图形状改变后沿用已有的图片失效规则。网络失败保留已有资料与内存图片。清除缓存使用代次隔离本地、远程及元数据回写，避免晚到请求复活已经清除的内容。

批量任务从宿主艺人 repository 的原始 `Flow<List<Artist>>` 读取完整快照，读取前检查 `library-read` 授权；不能从当前搜索网格推导全部艺人，也不从扁平曲目标签拆分名字，以免把 `AC/DC` 等名称拆坏。1.19.1/1.19.2 为静态 Flow getter，1.19.3 改为 companion 获取 repository 实例。版本目标集中在 `HookTargets`，复核入口见 [兼容记录](host-compatibility.md)。

批量协调线程一次只提交一个艺人，静态资料和图片走 Apple 优先队列，当前页面请求优先于尚未开始的批量请求。静态阶段完成后通过 future 衔接独立视频 worker 的选流和完整下载；不在 Apple 队列等待大视频，也不在视频 worker 等待自己排队的任务。下载只保存编码文件，不为全库生成模糊位图或解码视频。目录小头像可从预下载头像生成 320px 缩略图。界面仅显示已缓存与未匹配或暂不可用；有动态素材时，视频成功落盘后才计完成，失败保留已下载内容。取消等待当前艺人（含视频）结束，切页继续，停用释放所有队列。

按用户新增要求，一键下载包含动态头图完整视频。任务开始时捕获分辨率设置，沿用播放的最高可用 SDR 选流及回退策略；播放开关只控制显示，不阻止显式批量下载。视频缓存按 master URL 与所选质量隔离，同档缓存直接复用，切换档位后独立保存。离线下载与首帧后的后台缓存共用 in-flight 任务；同档不重复下载。清空/关闭推进代次，阻止旧选流的 `.stream` 与旧视频迟到回写，新代次同 key 不复用旧任务，完成回调在缓存锁外运行。

原来为限制磁盘占用而设的 8 个视频、总计 512 MiB 淘汰按用户要求移除；磁盘视频保留到用户清除缓存。64 项只是内存中的选流地址索引，不删除磁盘文件；128 MiB 单文件输入校验仍保留，两者不属于本次取消的磁盘保留限制。无动态素材的艺人照常按已有资料完成；已发现动态素材但无法完整离线保存时，内部保持可重试，界面计入未匹配或暂不可用。

266 项测试在完整 JDK 和宿主模块范围下通过，覆盖质量快照透传、异步视频阶段不占用 Apple 队列、完成计数、取消、下载去重、清空/关闭的代次隔离、锁外回调，以及 10 段视频和逻辑总量 600 MiB 仍不淘汰。另使用宿主运行时的生产批量入口，未启动播放器即下载 Marshmello 的 4K 视频（50,904,610 字节），任务已缓存为 1，元数据离线重载及无网络回调的视频复用通过；随后单独用生产 CPU 后端从该本地文件取得 3840×2160 连续变化帧。证据在 `build/reports/offline-motion-download/`，验证未修改用户缓存或运行中的宿主。

0.3.1 曾在 `BasicScreenBox` 上方再次组合原生 tools 和 body，覆盖了 0.3.0 的增强总列表，也带来重复列表组合和用户反馈的卡顿。本次恢复 0.3.0 的 `ArtistDirectoryHost`：读取宿主 ViewModel 的原始 StateFlow，在导航槽位绘制已有的增强总列表，保留网格、列表、大小、排序、隐藏项、浏览位置和原生界面切换。底下的宿主原生列表仍会组合，这是既有 `afterComposable` 覆盖方式的代价；不再额外重建一套原生 body。准备态和主题契约不满足时回退原生界面。

跟随椒盐设置时直接读取宿主 `SaltTheme` 当前 config 与配色，不再使用 Compose 的操作系统主题；读取快照状态以响应宿主外观变化。自定义时通过 config 局部副本选择深浅文字，保留原 indication，不修改全局配置或侧栏主题。自定义图片加暗色遮罩，路径丢失时回退自定义纯色。旧 `LIGHT`、`DARK` 选择迁移为跟随椒盐；旧 `SYSTEM` 键保持兼容但语义改为跟随椒盐。总列表背景使用单独配置，不改变详情页外观。

0.3.6 保留「跟随椒盐设置」和「自定义」两项，前者同时跟随深浅主题和椒盐窗口样式。1.19.3 宿主的 `AppConfig.getSpwWindowStyle()` 返回 `None`、`WindowsAcrylic`、`WindowsMica` 或 `WindowsMicaAlt`；插件读取其状态而不写入宿主配置。四种已识别样式均在绘制插件内容前对目录区域使用 `BlendMode.Clear`，露出宿主背景并恢复导航叠色；未知样式或接口不可用时回退主题色。自定义和原生界面切换不清除窗口。此前试验的 `MATERIAL` 值迁移为跟随椒盐。

增强目录仍通过 `afterComposable` 覆盖原生目录，单纯透明会透出原生内容；宿主定位器确认更细的容器与列表调用存在重复引用，不能仅凭方法签名安全替换。清除区域后依赖宿主背景位于同一绘制层之下，实际宿主窗口中的各材质和壁纸仍须验收。

用户实测发现清除区域与顶部存在明显色差。1.19.3 的导航背景使用 `navigationContentBackgroundColor`，清除操作连此层一并擦掉，露出未经相同叠色处理的底层；亮色与暗色均可能产生差异。第一次修复错误地认为迷你播放器背景保留条件为真时不需要叠色；用户实测仍有色差。复核宿主字节码发现，该条件只决定在 `NavigationContentSurface` 或外层 `NavigationBackground` 绘制同一叠色，清除之后两种情况都需要恢复。修复读取宿主实时颜色，不再用该条件跳过；接口缺失时回退透明并记录一次诊断。1.19.3 字节码确认浅色为 `#64FFFFFF`、深色为 `#1E3A3A3A`，实现不固定这两个值。隔离测试优先加载实际 1.19.3 归档和宿主 Skia，调用真正的宿主叠色及 `NavigationBackground`，并模拟另一条内容表面绘制路径，比较两种主题的上下像素；实际宿主窗口仍须验收。

经典样式也需要这层导航叠色，直接使用主题底色会与原生页面不同。离开目录时，宿主先保留旧页面，再将其作为独立层淡出；若旧页面持续绘制叠色，就会在已叠色的背景上短暂出现矩形。插件读取宿主导航栈及实际淡出动画，仅在旧页面开始淡出后停止恢复叠色，避免固定延时导致不同帧率下闪现；继续清除原生目录内容，避免露出底下的旧列表。相关入口只在已核实的 1.19.3 配置中启用，读取失败时保留旧行为。离屏测试使用真实宿主主题、导航动画作用域和导航栈，并覆盖不同帧间隔和进出方向；这不等同于实际窗口验收。

进入目录时，宿主可能已显示就绪列表，而插件后台转换尚未完成；两者之间原生列表会偶尔露出一帧。就绪状态转换期间先绘制当前背景，转换完成后显示增强目录；宿主加载和错误状态、用户主动切换到原生界面以及转换失败时仍显示原生界面，不以空白背景遮住错误。离屏测试覆盖首次绘制、转换成功与失败和主动切换原生界面。

总列表的移除、恢复、设置菜单及下载和背景面板使用同一套浅色或深色浮层和文字配色；自定义纯色依据亮度选择文字，并在强调色对比不足时回退高对比文字色。背景图片按最亮的遮罩后像素校验按钮配色。网格、列表和恢复面板共用固定正方形尺寸绘制的圆形选择控件，避免不同字体的勾号和空心圆导致形状不一致。

收藏星标恢复 0.3.0 的样式：网格和列表中使用名称前缀 `★ `，同时识别宿主和插件收藏；关闭收藏优先仅影响顺序，纯头像视图沿用原先不显示名称的行为。宿主准备态解析与曲库统计改在后台计算，UI 线程只提交结果；状态变化时取消过期的解析任务。原生列表增强在自定义总列表接入失败时仍按原有守卫降级。上述修改减少可识别的主线程工作和一次多余的原生 body 组合，未做实际宿主帧时间测量，仍需用户验收。

验证包含任务取消与重新开始、队列优先级、缓存先显示、一天刷新、失败保留旧资料、清除后拒绝迟到回写，以及背景解析、持久化和保存失败回滚。实际运行结果与尚未验证的宿主场景记在兼容记录中。



## 0.2.5 按艺人缓存与本地优先

0.2.4 的身份键包含整份手动绑定配置：给 B 添加绑定也会改变 A 的图片与元数据键。实际诊断日志和文件中，同一艺人出现多个 `aliases-v2` 命名空间。详情页还将磁盘命中排在单个联网 worker 后，列表缩略图既不复用详情头像，又可能在旧失败结果的十分钟冷却期内继续显示封面。0.2.3 的可见卡片保留引用只能防止组合内降级，无法修复这些跨页面、跨重启的问题。

`artistCacheToken(name)` 只纳入该艺人的有效绑定、识别开关、匹配规则版本与地区顺序；原名的规范化摘要继续隔离标点，资料语言仍独立保存。整份配置摘要仅用于旧版迁移和界面配置观察。迁移只接受当前旧版完整策略，或同一原名、相同显式 ID 的 v2 记录，并复制匹配模板的已有图片；不凭文件名猜测无绑定的历史身份，不混用新格式下不同地区的缓存。匹配更改保留已确认素材，显式「刷新头图」才清除该艺人的全部派生缓存；自定义头图不再清掉 AM 头像。

详情图片先在专用本地 worker 中读取、解码并发布，缺失或过期部分再交给联网队列。小于 1 KiB 的有效艺术字不再被误判为未缓存。大图 LRU 继续保持 4 项，避免以大量解码位图换取表面速度；淘汰后从磁盘恢复，不重新匹配。列表优先读取 320px 缩略图，缺失时直接从本地 900px 详情头像生成；详情加载完成会补救列表的旧失败结果。缩略图内存仍限 512 项，过期或刷新失败保留已成功的图片。

元数据、图片和缩略图采用临时文件原子替换。刷新按艺人推进请求代次，磁盘写入与结果发布都验证代次；迟到失败不能覆盖成功头像，其他艺人的请求不受影响。详情到列表的补热与普通列表请求分别去重，保证补热不会被正在结束的缓存未命中任务吞掉。

166 项自动测试覆盖绑定独立性、等价 ID／链接、旧缓存安全迁移与重载、地区隔离、标点隔离、刷新后拒绝旧资料、原子替换及清空代次。隔离 Skia 运行场景验证联网队列阻塞时本地头图仍先就绪、大图淘汰后的磁盘恢复、900px 到 320px 复用、旧失败结果补救、失败不覆盖成功及重启后零联网命中。用户实际缓存的只读副本中，三个已有手动匹配均能在离线条件恢复头图和列表头像；原缓存未修改。运行证据在本地 `build/reports/cache-025/`，宿主界面验收仍由用户完成。

## 0.2.2 CPU 视频输出与紧凑目录

用户反馈 30 帧设置仍不如 AM 流畅。用同一 bbno$ 本地视频、取帧／创建独立 raster 的计时路径复测，旧截图方案在 1080p／2K／4K 分别约 14.8／13.9／7.0 fps。mpv 的 [screenshot 实现](https://github.com/mpv-player/mpv/blob/master/player/screenshot.c) 每次截图等待 VO 并重建颜色转换器，默认高质量转换进一步增加开销；仅换 bilinear 与快速转换虽可改善到约 28.1／18.5／20.8 fps，仍有不规则等待，因此不只调整目标帧率。

改用 [mpv SW render API](https://github.com/mpv-player/mpv/blob/master/include/mpv/render.h)，API 类型明确为 `sw`，仍为独立 libmpv core、软件解码和普通 raster 绘制，不接回曾导致退出的宿主 Surface、共享纹理或 GPU render backend。颜色转换器与 64 字节对齐的 CPU 缓冲在会话内复用，只在收到新视频帧时转换。采用 bilinear／fast 色彩转换，保留所选片源分辨率，不通过缩小视频改善数字。高质量静态头图不受影响。

通过只读 dwidth／dheight property-change 事件取得实际画面尺寸，低分辨率片源不会被假放大成 2K／4K；缓冲继续有 3840×2160 与 64 MiB 上限。x64 `mpv_render_param` 是 16 字节条目，数组以 type=0 结束；格式为 bgr0、stride 为 size_t，数据与行距按 64 字节对齐。渲染线程只调用 render API 和 [client.h](https://github.com/mpv-player/mpv/blob/master/include/mpv/client.h) 明确允许的非阻塞 wait_event(0)，不使用阻塞的 core 属性查询，也不启用 advanced control 或 native 回调。read／close 由同一锁串行化，先 free render context、再 terminate core、最后释放 CPU 缓冲；API 不可用时保留经过验证的截图回退。

CPU 缓冲仍复制为独立不可变 Skia 图像，再发布到 OwnedMotionFrame；拒绝复用仍被图像引用的裸指针，避免为减少一次复制重新引入绘制与释放竞争。帧间隔改为持续时间线，跳过长停顿后的过期时隙，防止逐次舍入和转换耗时累积。无新帧时只短暂轮询，不等待完整的 1/30 秒而错过即将到达的帧。Compose 通过 withFrameNanos 合并最新帧、在普通独立绘制层刷新，避免后台更新与显示刷新各自漂移；隐藏、失焦和销毁仍结束会话。

生产实现隔离取帧含 raster 创建，30 档得到约 29.85／29.81／27.74 fps，24 档约 23.90／23.81／23.98 fps；1080p 帧间隔 p95 从约 75 ms 降到 35 ms。4K 仍受 CPU 和复制开销限制，不能承诺所有硬件满帧。使用真实 Compose／Skia 离屏场景验证三档动态画面内容持续变化、虚化、失焦释放与恢复，以及切换档位后单一播放器存活。另验证缓冲复用和销毁后已发布 raster 不变、并发 read／close、1080p 在 4K 上限下仍输出原尺寸，以及旧截图后端可回退。证据在本地 `build/reports/smooth-022/`；不以这些隔离结果声称宿主最终呈现帧率，宿主交互仍由用户验收。

目录按用户最后更正，将搜索、排序入口、原生界面的返回箭头都放在右上角。菜单用四种视图图标和三档分段大小选项替代长文字，只保留五种排序；旧 NATIVE 配置按名称排序回退。「原生界面」直接撤下插件列表，只留右上角小箭头。离屏语义交互验证搜索／返回的位置、多选移除恢复、视图大小排序保存与重载，以及 Loading→Ready。

## 0.1.9 动态渲染替换

用户确认 0.1.7 开启动态头图退出、关闭则不退出，将问题定位到动态路径，但没有定位到单条 native 崩溃指令。0.1.9 移除宿主视频 Surface、反射 Composable 和共享 GPU 视频纹理接入，恢复配置开关，使用独立 libmpv C API 实例（vo=null、hwdec=no、音轨关闭）读取 screenshot-raw CPU 帧，再通过普通 Skia raster Image 绘制。主机 GPU 仍负责普通 UI 绘制，但不再接收解码器的共享纹理或跨库视频 Surface。

MediaMP JNI handle 是包装对象地址，不能当作 libmpv C API handle。实现只用 mpv_create 返回的独立 handle，按 [mpv 官方 client.h](https://github.com/mpv-player/mpv/blob/master/include/mpv/client.h) 的 x64 mpv_node/map/byte-array ABI 读取、复制并释放结果；不访问 MediaMP 包装对象内部内存。宿主 factory 仅用于加载已有 native 库，随即关闭，不创建 Surface。JNA 仅 compileOnly，未打入插件。

0.1.9 当时每秒最多取 10 帧；0.2.0 已改为上文的目标帧率与复制策略。H.264 SDR 流选择已由 0.1.10 改为上文的清晰度策略，像素/stride/字节数校验后复制到 JVM 数组。OwnedMotionFrame 在替换、绘制和释放间互斥；绘制方法返回后才释放旧 raster Image，关闭后晚到帧立即释放，不积累逐帧位图。解码与销毁在后台进行，窗口失焦、切页、插件停用均结束会话。

隔离 probe 已取得 Gorillaz 24 张内容不同的真实 CPU 帧，并经过 Skia raster Image 编码输出 PNG，确认通道与画面正确，不再只验证播放时钟。未操作宿主应用；实际宿主动态页面仍需用户验收。证据在 build/reports/motion-research/raw-probe.log、cpu-frame.png。下文 0.1.7 的 GPU Surface 设计仅为历史，不是当前播放路径。

最终生产类另完成 3 轮独立创建、取帧、销毁，每轮取得 5 帧；结果在 raw-probe-final.log。125 项自动测试及打包检查通过，新增覆盖绘制过程中禁止释放帧、替换与停用后迟到帧仅释放一次。测试、隔离 CPU 绘制验证与宿主实际验收仍分别记录。

`recognize_artist_aliases` 默认开启。选择顺序是用户手动绑定、已验证的内置指定 ID、名称或别名相关的自动候选。扩展表中的指定 ID 仍需官方 lookup 名称验证；原有七组指定 ID 验证失败时不退回同名猜测。没有直接相关的候选时，至多对三个候选做官方 lookup 或页面标题核验；没有相关证据时回退曲库图片。

多个相关候选不再要求用户选择：查询至多两个有效地区的 iTunes 歌曲搜索结果，按候选 artist ID 统计去重歌曲（最多计 12 首），每首 3 分；艺人搜索中出现的地区每个 2 分（最多 3 个）。前两名差距不超过 6 分时，最多读取两张候选原生艺人页，确认属于该 ID 的动态头图加 6 分；最终按分数、搜索位置与稳定原始顺序选出一个。未取得数据不是零粉丝；Apple 公共艺人资料不提供通用粉丝数或播放次数，这里的歌曲出现次数、地区和动态头图均只是弱代理，不能称为播放量或准确热度。最终同分时自动使用搜索位置，可能选错。搜索最多增加两个别名变体、每个至多两个地区；优先保留已有后台队列和缓存节流，避免整库并发请求。

传输失败或非法响应继续尝试其他地区，空结果与失败分开；无信号时仍从名称相关的候选中自动选择。严格模式保持原有首个可用地区的完整名称行为。用户绑定不依赖名称相似，仅验证指定 ID 存在；开关关闭仍忽略绑定与别名。此策略替代 0.1.7 遇到同名即拒绝的规则，也保留早期范围验证与 ID 一致性检查。

更多菜单的「匹配 Apple Music 艺人」提供显式选择：可按名字搜索，展示相似候选，或输入官方艺人链接、纯 ID。搜索候选不代表自动确认，用户选择后才写入当前原始曲库名的绑定；可删除该绑定恢复自动匹配。保存选择时若别名识别已关闭，会同时开启识别。该入口不重命名艺人、不改变曲目聚合；自动选择仅作用于 Apple Music 素材身份。

`artist_identity_overrides` 为设置文本框，格式为「曲库艺人名=Apple Music 官方 HTTPS 艺人链接或纯 ID」，链接形如 `https://music.apple.com/{store}/artist/[slug/]ID`；多项使用英文分号或换行，例如 `初音未来=307078957;周杰伦=300117743`。该映射关联原始曲库艺人名，不重命名显示条目，也不改变保存编辑与收藏时的身份。

链接解析必须验证官方域名与完整艺人路径，不能从任意包含 `artist` 或尾部数字的路径宽松截取 ID。完整路径限制与 canonical 验证失败后的回退约束均有针对性测试。

手动绑定需要开启别名识别，关闭开关时手动与自动绑定均忽略。身份键规范化宽度、大小写与空白，清除常见不可见分隔符，保留标点后取 SHA 指纹。0.1.7 的 namespace 包含原名 SHA、`strict-v2` 或 `aliases-v2`、规范化的地区顺序，开启模式还包含手动绑定摘要。两种模式均区分 `AC/DC` 与 `AC DC`，不能仅用折叠标点的艺人名作 AM 缓存键。

0.3.0 的自动别名匹配使用 `aliases-v4` 单艺人 namespace，旧自动结果不迁入，以便重新计算可能有误的身份；旧文件保留，首次加载会重新联网。明确的手动 ID 和严格模式继续使用各自的 `v3` namespace，不因其他人的设置变化而失效。

0.1.4 的旧 name-only 缓存没有足够身份信息，后续版本不复用这些记录作为新策略身份。0.1.7 再以策略 v2 隔离旧策略结果，升级后按需重新确认，无需用户手动清理。旧格式仍可解码，但不代表旧 namespace 可作为新策略命中；同一 namespace 下各语言缓存仍可落盘并重载。开关、地区顺序与手动绑定内容共同隔离元数据、大图、头像的成功与失败结果；刷新某艺人时清除该原名下全部策略 namespace。头图、头像与资料共用同一不可变识别策略，后台请求晚到也写回其原策略缓存。

## 地区顺序与传输回退

`apple_music_storefronts` 默认 `US,JP,CN`。配置接受最多 8 个不同的合法 ISO 两字母地区代码，保留用户顺序；无有效输入时恢复默认。地区顺序参与身份 namespace，资料语言独立控制页面或公开资料接口的 locale，选 CN 不等于强制中文，也不能假设 US 页面只包含英语。

仅默认地区顺序启用临时 US 健康回退：US 网络请求失败或响应不合法后，本次接着先尝试 CN、再 JP，随后 5 分钟暂避 US。有效的空搜索列表不触发暂避；没有某艺人或没有某字段也不能直接当作地区网络故障。自定义地区顺序按配置尝试，不被该默认策略重排。

地区健康只是内存中的短期传输状态，不写入配置、资料或图片缓存的 namespace。它不能改写艺人 ID、资料语言或永久覆盖用户选择；配置的地区顺序本身才是缓存身份的一部分。

## 资料语言与回退

首选语言可设为 `CHINESE`、`ENGLISH` 或 `JAPANESE`，默认中文。`showOtherLanguages` 默认开启：首选语言没有资料时允许显示其他可用语言的原文；关闭后按所选语言筛选，不自动翻译或补造内容。身份识别 namespace 内的资料缓存再按艺人与语言区分；切换首选语言或回退设置后应用新的偏好，不能继续展示不符合当前设置的旧选择。日期仍沿用中文格式，语言偏好控制资料选择而非自动翻译界面。

显式中文 URL 不保证返回中文正文；实际为英文时标记为 EN，并尝试原生 US `en-US` 页。只有允许其他语言时才展示这种降级资料；中文偏好关闭语言回退时，也过滤未翻译的来自和流派。某些艺人在中文页没有简介、英语页却有原文，不能把这种情况当作全部资料缺失或生成中文简介。

中文页的结构化数据可能提前包含英文简介，这段降级资料不能抢占显式 US `en-US` 页的英语选择；0.1.4 语言测试拦住该问题后修正了来源优先级，不能改回全局取首段可用简介。

公开页面按目标艺人 ID 绑定 header、结构化数据和简介，避免取到推荐艺人的图片或文字。公开资料接口补充基础字段；app bearer 从当前公开网页资产动态发现，仅存内存，不落盘、不写日志，不要求用户登录。字段缺失正常回退，不能假设所有艺人都有完整中文资料。远程资料请求与本地照片、封面解码保持独立后台任务。

## 当前 poster 与动态头图

同一艺人在同一区域的不同页面语言也可能返回不同动态素材：2026-11-04 实测 Roddy Ricch 的 US 英文页和 US 简体中文页返回不同的横向视频。为保持中文简介同时使用用户期望的头图，0.3.0 将 `artist_visual_storefront`（最多八个 ISO 两位地区代码，默认顺序 `US,JP,CN`）与 `artist_visual_language`（默认英语）独立于简介语言及身份搜索地区。按用户顺序选择首个包含可显示动态头图的地区；全部没有动态版本时选择最靠前的可用静态头图，均不可用时回退曲库封面。只填一个地区则不追加其他地区，早期单地区设置沿用原值。所有请求保持用户选择的头图语言，不根据艺人名字、简介语言或资料店铺猜测国籍。

视觉元数据、动态视频 URL 与同一 variant 的 poster 按身份、完整地区顺序和页面语言独立缓存；原有简介、头像与手动绑定仍用原策略。相同顺序的缓存可跨重启复用，切换顺序不会串用另一版本的本地 poster；请求失败或响应无法解析时，当前可用的替补素材可以展示，但不标记为长期新鲜结果，以便下次重试前面的地区。刷新或清理按艺人清除各来源。视觉请求使用现有后台执行器及请求代次；这些设计兼顾原 0.2.5 的本地优先和迟到响应隔离。已通过合成资料顺序切换、缓存重载、失败恢复与静态回退验证，Roddy Ricch 的两种真实页面素材解析也已验证；宿主设置面板及显示效果仍需交互验收。

动态素材只从目标 `ArtistDetailPageIntent` 下唯一且 ID 一致的 `artistDetailHeader` 读取。优先 `wideVideoArtwork.dictionary.motionArtistFullscreen16x9`，再尝试 `motionArtistWide16x9` 和 `videoArtwork.motionArtistSquare1x1`，将同一 variant 的 `video` 与 `previewFrame.url` 绑定；不在推荐区或整页文本中寻找视频。

公开 [Gorillaz 艺人页](https://music.apple.com/us/artist/gorillaz/567072?l=en-US) 的 US、CN、JP header 已核实同时包含旧 `wideArtwork` 和新的动态 variant。旧解析无条件优先静态横图，因此即使页面已换动态素材，插件仍会显示旧图。0.1.7 优先当前动画的官方 poster，关闭动画也使用这一静态图；poster 是官方提供的预览画面，不保证等于视频解码的第零帧。

元数据的可选 `AmArtistMotion` 保存 HLS/MP4 类型、视频 URL 和同 variant 的 poster；`motionCheckedAt` 区分「已检查且没有动画」与旧版、仅头像缓存的「尚未检查」。v4 缓存使用固定 24 列，兼容读取旧 8 列、v2/v3 的图片与资料，但旧记录需要补查一次 header。动态开关不参与元数据身份，不因开关反复抓取同一艺人的资料。

URL 只接受已知 Apple CDN 的 HTTPS HLS/MP4 和图片模板，拒绝本地协议、外部域、账号信息、非默认端口与过长 URL；页面与缓存行也有大小限制。实测 Gorillaz master 提供 SDR H.264 与 HEVC 多码率 variant，播放器优先普通 H.264 SDR 视频流，不能把 I-frame trick-play 列表误当完整动画。最小无简介网络证据保存在本地 `build/reports/apple-music-motion/`，不随包分发第三方视频。

`animated_artist_hero` 默认开启，仅当当前素材来自 AM 且没有自定义照片时尝试播放。复用宿主 mediamp/mpv，以独立播放器静音循环，不修改音乐播放队列、不新增解码器或视频分发包。poster 位于动画下方，待实际帧就绪后再显示视频；失败保留 poster。动画与静态图共用底缘渐隐和裁剪，头图滚出约 60% 或窗口失焦时离开组合并释放资源，重新进入时按当前艺人素材建立会话。

隔离无窗口 harness 已验证宿主 factory 自行加载内置 native 库，无额外库路径或解码器安装；Gorillaz 的 H.264 1024×576 视频解码时间持续推进，音轨关闭、静音和循环参数被接受。Surface 的字节码已确认直接消费 native 视频纹理，不依赖未设置的 high-level currentMedia。此验证未创建 Compose GPU 页面，实际画面与交互仍由用户验收。宿主反射 ABI 与失败边界见 [兼容记录](host-compatibility.md#动态头图运行时约束)。

## 0.1.x 艺人总列表扩展（0.2.0 注册失败时的回退）

沿用的列表增强依据宿主 1.19.1 的字节码与当前 Compose 内部契约设计，0.1.6 已复核 1.19.2 的相关目录与 Compose class 字节未变，仍待用户手动验收。目标是在不改变宿主数据源、布局尺寸和点击行为的前提下，提供收藏优先和 Apple Music 小圆头像；任何守卫失败都保留原生行为。0.1.5 的别名识别只改变头像资源的目标，不重排或合并艺人条目。

`favoritesFirst` 默认开启，使用稳定分组：收藏艺人置前，收藏组和其余组内部各自保留宿主原顺序。关闭时沿用原始顺序；不修改宿主的 List 或 Flow，不给其他页面的数据消费者重排源数据。

排序接入采用官方 `appendContent` 包裹原 grid DSL。先从本次临时 `LazyGridIntervalContent` 读取 `intervals`，在契约守卫通过后生成索引映射，复用原有 `key`、`contentType` 和 `itemContent`。完整映射准备好后，原子替换本次临时 builder 的引用，使一次构建使用一致的映射；失败时不留下部分重排。

`ComposableLambdaImpl` 同时实现多个 FunctionN 接口，普通 Kotlin 函数类型转换还会检查 arity，曾误拒绝符合 grid JVM 契约的回调。现先用 Java `Function4.isInstance` 验证接口，再使用泛型擦除转换；真实 `invoke` 签名已对照宿主与依赖，升级时须保留这一核查。该问题由真实 Compose interval builder 测试发现并修复。

没有采用以下两条已核对过的路径：`after.setResult` 的结果未被宿主回写，不能改变最终 grid 内容；`replaceGrid` 在该调用点被 `defaultMask=1008` 跳过。使用临时 builder 映射是针对这些约束的选择，并不表示 Compose 内部结构是稳定公开 API。宿主或 Compose 升级时必须重新核查该契约与守卫，不能只扩大版本范围。

头像接入保留原生 48dp 头像的绘制与测量，不替换原生 Composable。`afterComposable` 追加零宽、48dp 高的容器，在内部绘制固定圆图覆盖原头像。字节码已确认目标父 Row 使用 Start 排列并有显式 Spacer，因此设计上不重新分配水平空间；原有点击仍由宿主维持。零宽覆盖的实际对齐、裁剪和点击保持仍需在目标宿主运行验证。

## 列表头像加载约束

列表头像走独立轻量路径：仅可见项按需请求 320px 图片，0.2.3 起内存最多 512 项并按最近使用淘汰，使用磁盘缓存，单个网络 worker 渐进加载并节流。0.1.5 在身份解析中应用同一别名与手动绑定策略，再读取目标公开页的头像元数据；仍不访问资料接口或大型网页脚本，也不下载 hero 大图。

没有合适的 Apple Music 图、请求失败或图片尚未就绪时，不遮住原生曲库封面。加载成功后才显示覆盖图。此回退与稳定排序分别受守卫约束，不能因头像不可得而丢掉列表项或改变点击对象。

## 艺人页沿用的约束

0.1.3 将顶栏右侧改为直接搜索，复制摘要移入更多菜单；「自定义艺术字」支持透明 PNG/WebP 的解码验证、预览与恢复默认，路径丢失也能恢复。自定义图片、艺术字、显示名与曲目覆盖使用原始艺人键保存；编辑器保留隐藏原曲与手动添加曲目的快照，别名和歌曲 ID、原始专辑键分开。

0.1.1 的标题已经居中，但主播放与随机播放位于分离的偏左动作区，其他操作集中在顶栏胶囊；0.1.2 将主信息和动作聚合到中心。写真沿用宽范围渐隐，从照片下缘取色，调暗时保留色相；清晰层、模糊层与背景共同收敛到同一底色，避免短渐变或硬色块强调横向接缝。遮罩位于照片和背景层，保持文字可读。专辑网格按内容宽度 1100/860/620dp 对应六/五/四列，更窄时两列。

侧边栏和系统标题栏仍在艺人页槽位之外。主页面的 `afterComposable`、权限描述符和逐版混淆映射以 [宿主兼容记录](host-compatibility.md) 为准；新增的列表接入契约见本记录。配置页「暗色背景」尚未被页面消费，仍为已知问题。

添加时间不依赖 `RepoService.snapshotTracks`：0.1.3 首候选显示 255 首曲目但已知添加时间为 0，字节码确认该快照由独立流程更新。现有路径在公开曲库读取成功后，复用 Library 实现的原始只读 Track 查询，后台适配立即结果或挂起 Continuation，8 秒超时后降级；缓存绑定曲目列表身份，并通过加载代次丢弃过期回调。
